### Исследовательский вопрос

**При каких объёмах документов и типах вопросов длинный контекст превосходит RAG и наоборот?**

### Что сделать (чек-лист заказчика)

1. Создать связанные документы объёмом 8K, 30K и до 100K токенов.
2. Подготовить вопросы на простой факт, сравнение двух документов и поиск противоречий.
3. Сравнить передачу всех документов в длинный контекст, BM25+LLM и Embedding RAG+LLM.
4. Проверить доказательства, ссылки, latency и стоимость.
5. Отдельно проверить положение факта в начале, середине и конце контекста.

### Данные

30–50 публичных нормативных или собственных тестовых документов с контролируемыми фактами. Только открытые, собственные или разрешённые данные.

### Метрики

Accuracy, evidence recall, citation correctness, latency, $/correct. Эксперимент на 100K ограничить доступным бюджетом.

### Что показать

Воспроизводимый benchmark, сравнение конфигураций, измеренную стоимость и выводы о практическом применении в KOZ AI.

## 2. Три решения, которые определяют весь проект

Принять их до написания первой строчки кода.

### 2.1 Факты внедряются, а не размечаются

Главная ловушка research-проекта в одиночку — ручная разметка. Если взять 40 реальных документов и размечать по ним вопросы и эталонные фрагменты, уйдёт 3–4 дня, и срок сгорит.

Решение: **корпус реальных документов как фон + внедрённые контролируемые факты**. Берём публичные нормативные документы как реалистичный шум, вставляем в них собственные утверждения с известным содержанием, известным документом и известной позицией.

Что это даёт:

- Gold-ответ известен по построению — размечать нечего.
- **Evidence recall считается точно, без LLM-судьи**: мы знаем id чанка, в который вставлен факт, и просто проверяем, попал ли он в выдачу. Это точная метрика, а не оценочная — сильный аргумент на защите.
- Citation correctness тоже точная: знаем правильный документ.
- Позиционный эксперимент возможен в принципе — мы управляем местом вставки.
- Противоречия можно внедрить парами в заданные документы, а не искать их в природе.

Судья LLM остаётся только для одной метрики — accuracy самого текста ответа. Всё остальное считается детерминированно.

### 2.2 Единственное, что меняется между конфигурациями, — контекст

Промпт, модель, температура, формат ответа, судья — одинаковые для long context, BM25 и embedding RAG. Если у long context будет свой промпт, сравнение невалидно и его разберут на защите.

Один шаблон, одна функция генерации ответа, три разных способа собрать `{context}`.

### 2.3 Честное сравнение требует выравнивания по бюджету токенов

Long context получает весь корпус, RAG — top-k чанков. Это сравнение «много контекста против мало контекста», а не «архитектура против архитектуры». Поэтому кроме основного прогона делаем контрольный:

**RAG с выровненным бюджетом** — увеличиваем k, пока RAG не займёт столько же токенов, сколько long context. Если RAG при равном бюджете всё ещё лучше — вывод сильный. Если хуже — тоже честный результат.

Эта ablation занимает полдня и отличает серьёзную работу от студенческой.

## 3. Дизайн эксперимента

### 3.1 Факторы

| Фактор | Уровни |
|---|---|
| Размер корпуса | 8K · 30K · 100K токенов |
| Метод | LC (long context) · BM25 · EMB (embedding RAG) · [опц.] HYB (BM25+EMB+reranker) |
| Тип вопроса | T1 простой факт · T2 сравнение двух документов · T3 поиск противоречий |
| Позиция факта | 0% · 25% · 50% · 75% · 100% от длины контекста |

Полный перебор не нужен и не влезет в бюджет. Разбиваем на три уровня (раздел 5).

### 3.2 Типы вопросов

**T1 — простой факт.** Ответ содержится в одном месте одного документа.
> «Какой срок рассмотрения заявления установлен в регламенте X?»

Ожидание: RAG не хуже LC и в десятки раз дешевле.

**T2 — сравнение двух документов.** Ответ требует фактов из двух разных документов одновременно.
> «Отличается ли срок рассмотрения в регламенте X и в регламенте Y?»

Ожидание: LC выигрывает, RAG проваливается, когда вытаскивает только одну сторону. Чинится ростом k или декомпозицией запроса — это и проверяем.

**T3 — поиск противоречий.** Два внедрённых утверждения несовместимы, вопрос требует это обнаружить.
> «Есть ли в корпусе противоречащие друг другу требования к сроку хранения документов?»

Ожидание: самый тяжёлый тип для RAG, потому что нужно удержать оба фрагмента сразу и заметить конфликт.

По 20 вопросов каждого типа = **60 вопросов**.

### 3.3 Позиционный эксперимент (Lost in the Middle)

Заказчик требует отдельно. Делаем две версии — вторая выходит за рамки задания и усиливает работу.

**P1 — позиция в полном контексте (для LC).** Один и тот же факт вставляется на 0 / 25 / 50 / 75 / 100% длины корпуса, вопрос один и тот же. Измеряем accuracy по позиции.

Ожидание: на 8K эффекта нет, на 100K провал в середине.

**P2 — позиция золотого чанка в выдаче (для RAG).** Искусственно ставим gold-чанк на ранг 1, 5, 10 в top-k при фиксированном k=10. Измеряем, теряет ли модель факт, который лежит в конце подборки.

Это прямой аналог lost-in-the-middle для RAG, и почти никто его не меряет. Хороший материал для отчёта.

### 3.4 Что считается контролируемым фактом

Утверждение, которое:
- не встречается в реальном корпусе и не выводится из него (иначе модель ответит из общих знаний);
- сформулировано в стиле окружающего текста;
- однозначно проверяется (число, дата, срок, наименование);
- вставлено в известный чанк известного документа.

Для T3 — пара утверждений в разных документах, несовместимых по смыслу.

Обязательная проверка: **прогон всех вопросов без контекста вообще**. Если модель отвечает правильно на пустом контексте, факт не контролируемый — его надо переписать. Эта проверка стоит копейки и спасает всю работу.

### Единый LLM-клиент

Весь код ходит в модель только через `src/llm_client.py`:

```python
def complete(messages, *, temperature=0.0, max_tokens=512) -> LLMResponse
def embed(texts) -> list[list[float]]
```

`LLMResponse` обязательно несёт `prompt_tokens`, `completion_tokens`, `cached_tokens`, `latency_ms`. Без этого нечего будет писать в метрики.

Переключение backend — переменной `LLM_BACKEND=openai|local`. Ни один другой файл не знает, какой backend активен.

### Воспроизводимость

Это benchmark, его главное свойство — воспроизводимость. Обязательно:

- все параметры в `configs/*.yaml`, ничего в коде;
- зафиксированные версии моделей в конфиге (не `gpt-4o-mini`, а полный идентификатор с датой);
- `seed` для всего случайного (выбор документов, перемешивание, выбор позиций);
- каждый прогон пишет `runs/<timestamp>/raw.jsonl` — по строке на вызов, с полным промптом, ответом, usage и latency;
- `pip freeze > requirements.lock.txt`;
- кэш ответов по хэшу промпта в `runs/cache/` — защищает бюджет при повторных запусках после падения.

## 5. Бюджет: как уложиться в $5

Самая реальная угроза проекту. Считаем заранее, а не по факту.

### 5.1 Арифметика

Стоимость одного вопроса в режиме LC ≈ размер корпуса × цена входного токена. Поэтому 100K-ячейка дороже 8K-ячейки примерно в 12 раз при том же числе вопросов.

Формула для планирования:

```
стоимость_ячейки = N_вопросов × N_повторов × (входные_токены × цена_вход
                                              + выходные_токены × цена_выход)
```

**Проверьте актуальные цены на странице OpenAI перед стартом** — тарифы и названия моделей меняются. Ниже структура расчёта с мини-моделью; подставьте свои числа в `scripts/estimate_cost.py` и получите точную смету до первого запуска.

### 5.2 Трёхуровневый план прогонов

**Уровень 1 — полная матрица на 8K и 30K (основной результат).**

60 вопросов × 3 метода × 2 размера × 3 повтора = 1080 вызовов.
Входные токены: LC даёт 8K и 30K на вопрос, RAG-методы примерно по 3K.
Порядок величины: около 9M входных токенов. Это основная часть сметы и при этом самая дешёвая часть на единицу результата.

**Уровень 2 — 100K ограниченно (карточка это прямо разрешает).**

24 вопроса (по 8 на тип) × 2 повтора × LC = 48 вызовов × 100K ≈ 4.8M токенов.
RAG на 100K стоит столько же, сколько на 8K — контекст остаётся ~3K, растёт только индекс. Это само по себе результат, который нужно подчеркнуть в отчёте.

**Уровень 3 — позиционный эксперимент.**

Основной прогон P1 делаем на 30K (дёшево), сокращённый на 100K: 3 позиции × 5 фактов × 1 повтор = 15 вызовов. P2 целиком дешёвый, контекст маленький.

**Судья.** Около 2000 оценок по ~1K токенов = ~2M токенов. Заложить отдельной строкой.

Суммарно укладывается в $5 с запасом примерно вдвое. Запас нужен — он уйдёт на перезапуски после багов.

### 5.3 Четыре приёма экономии

1. **Вся отладка — на локальной модели.** В OpenAI уходят только финальные зачётные прогоны. Это экономит больше, чем все остальные приёмы вместе.
2. **Prompt caching.** При LC корпус — это неизменный префикс промпта, а вопрос — изменяемый суффикс. Если ставить корпус в начало, повторные запросы по тому же корпусу попадают в кэш провайдера и входные токены считаются по сниженному тарифу. Логируйте `cached_tokens` и покажите в отчёте стоимость с кэшем и без — **это отдельный вывод для бизнеса**, потому что он меняет рекомендацию: для сценария «много вопросов к одному документу» LC дешевле, чем кажется.
3. **Кэш ответов на своей стороне** по хэшу (промпт + модель + параметры). Падение на 900-м вызове из 1080 не должно стоить денег.
4. **`cost_guard`** — жёсткий лимит из `.env`, счётчик в `runs/budget.json`, исключение при превышении. Ставится в первый день, а не после того, как деньги кончились.

### 5.4 Порядок запуска

Строго от дешёвого к дорогому: 8K → 30K → позиционный на 30K → 100K → позиционный на 100K. Если бюджет кончится, у вас уже будет полный результат на двух размерах и честная строка в отчёте «100K ограничен бюджетом», что карточка прямо допускает.

## 6. Два варианта LLM

### Вариант A — OpenAI (мини-модели)

| Компонент | Что брать |
|---|---|
| Генерация ответов | `gpt-4o-mini` / `gpt-4.1-mini` |
| Эмбеддинги | `text-embedding-3-small` |
| Судья | та же мини-модель |

Плюсы: ноль инфраструктуры, поддержка 100K+ контекста из коробки, prompt caching работает автоматически, usage приходит от API, результат воспроизводим у проверяющего.

Минусы: деньги, зависимость от сети.

### Вариант B — локально на GPU-сервере / DGX Spark

| Компонент | Что брать |
|---|---|
| Генерация | открытая instruct-модель 7–14B через vLLM |
| Эмбеддинги | `BAAI/bge-m3` (мультиязычная — критично для русского) |
| Реранкер (для HYB) | `BAAI/bge-reranker-v2-m3` |

Плюсы: бесплатно, неограниченное число прогонов, приватность данных, своя задержка как отдельный результат.

Минусы и подводные камни:

- **Длина контекста.** Номинальная поддержка 128K ≠ рабочая. Проверьте, что выбранная модель реально держит 100K, а не деградирует после 32K. Запустите короткий needle-тест до того, как строить на этом эксперимент.
- **KV-кэш на 100K.** Требует десятки гигабайт VRAM. На GPU-сервере проверьте через `--max-model-len` в vLLM, влезает ли.
- **Prefill 100K на DGX Spark будет медленным** — там большая память, но меньшая пропускная способность. Это не блокер, а отдельный интересный замер: «локальная задержка на длинном контексте против API».
- Проверьте актуальные имена и версии моделей на Hugging Face — они быстро устаревают.

### Рекомендуемая комбинация

- Разработка, отладка, все прогоны на 8K — **локально**.
- Финальные зачётные прогоны всех трёх уровней и судья — **OpenAI мини**.
- Отдельная таблица в отчёте: те же 8K и 30K на локальной модели — accuracy, latency, стоимость владения.

Так в работе появляется второе измерение (API против локального сервинга), которого в задании нет, бюджет остаётся целым, а в отчёте — вывод о том, когда вообще имеет смысл платить за API.

## 7. Метрики

| Метрика | Как считается | Тип |
|---|---|---|
| **Accuracy** | LLM-судья сравнивает ответ с gold; калибровка на 40 примерах вручную | оценочная |
| **Evidence recall** | gold-чанк ∈ переданный контекст | **точная** |
| **Citation correctness** | указанный документ == gold-документ | **точная** |
| **Hallucination rate** | ответ утверждает факт, которого нет в gold | оценочная |
| **Abstention rate** | доля «в контексте нет ответа» | точная |
| **Latency** | p50 и p95, отдельно retrieval и generation | точная |
| **Tokens/question** | prompt + completion + cached | точная |
| **$/correct** | суммарная стоимость ÷ число правильных ответов | производная |

### Почему $/correct — главная метрика

Accuracy сама по себе ничего не решает: LC почти всегда даст чуть больше правильных ответов, просто потому что видит всё. Вопрос бизнеса — сколько стоит один правильный ответ. Именно эта колонка превращает benchmark в рекомендацию.

### Про evidence recall у LC

У long context evidence recall равен 1.0 по определению — весь корпус в контексте. Если при этом accuracy у LC ниже, чем у RAG, вывод мощный: **узкое место не в поиске, а во внимании модели**. Это нужно прямо написать в отчёте, это и есть содержательный результат.

### Про судью

- Температура 0, фиксированный промпт, судья не знает, какой метод породил ответ (убрать из входа всё, что выдаёт метод).
- Калибровка: 40 примеров размечаются вручную, считается согласованность судьи с человеком, число идёт в отчёт. Без этого цифрам не поверят.
- 3 повтора каждого прогона, в таблицах среднее ± разброс. Даже при temperature=0 API недетерминирован.

### Про Ragas

Карточка его упоминает, поэтому подключить стоит, но осторожно. `context_recall` и `context_precision` у нас считаются **точно** по внедрённым фактам — это лучше, чем оценка Ragas. Используйте Ragas для `faithfulness` как вторичную проверку и напишите в отчёте, что основные retrieval-метрики считаются детерминированно, потому что факты контролируемые. Это осознанное решение в вашу пользу, а не пропуск инструмента.

## 8. Данные

### 8.1 Источник фонового корпуса

Нужно 30–50 документов на русском, тематически связанных (связность важна — она создаёт реалистичную трудность для поиска, когда похожие формулировки встречаются в нескольких документах).

Кандидаты:
- публичные нормативные акты и регламенты Казахстана;
- открытые стандарты и технические регламенты;
- публичные университетские положения и методички;
- открытые клинические руководства, если хочется переиспользовать опыт.

**Проверьте условия использования каждого источника** — карточка требует только открытые или разрешённые данные, и в отчёте нужна строка о происхождении корпуса.

Если с лицензиями возня, полностью синтетический корпус тоже допустим («собственные тестовые документы» разрешены явно). Потеряете в реалистичности, выиграете день.

### 8.2 Сборка корпусов

`build_corpus.py` собирает три корпуса **точно по токенам**, а не по числу документов:

- 8K — около 3–5 документов;
- 30K — около 12–18;
- 100K — все 30–50.

Корпуса вложенные: 8K ⊂ 30K ⊂ 100K. Тогда один и тот же вопрос осмысленно задавать на всех трёх размерах, и сравнение по размеру становится чистым — меняется только количество отвлекающего материала.

Счёт токенов — тем же токенайзером, что у целевой модели. Для локальной и OpenAI токенайзеры разные, поэтому фиксируйте, по какому считали, и укажите это в README.

### 8.3 Внедрение фактов

На каждый корпус:
- 20 одиночных фактов для T1;
- 20 пар связанных фактов в разных документах для T2;
- 20 пар противоречащих фактов для T3;
- 5 отдельных фактов для позиционного эксперимента, каждый вставляется в 5 позиций (отдельные варианты корпуса).

`gold.json` пишется автоматически в момент вставки:

```json
{
  "fact_id": "f_T1_007",
  "type": "T1",
  "statement": "Срок рассмотрения заявления составляет 14 рабочих дней",
  "answer": "14 рабочих дней",
  "doc_id": "doc_019",
  "chunk_id": "doc_019_c04",
  "position_pct": 42.7,
  "corpus_sizes": ["8k", "30k", "100k"],
  "paired_with": null
}
```

### 8.4 Генерация вопросов

Из `gold.json` по шаблонам, затем полировка локальной моделью под естественные формулировки. Проверка глазами — обязательна, но она быстрая, потому что ответ уже известен.

### 8.5 Обязательная проверка на утечку

`scripts/check_leakage.py` прогоняет все 60 вопросов с **пустым контекстом**. Любой вопрос, на который модель отвечает правильно без контекста, бракуется и переписывается. Дешёвая проверка, которая защищает весь результат.

## 11. Промпты

### 11.1 Ответ (один для всех методов)

```
Ответь на вопрос, опираясь ТОЛЬКО на приведённые документы.

Правила:
1. Если ответа в документах нет — напиши ровно: "В предоставленных документах ответа нет."
   Не достраивай из общих знаний.
2. Укажи идентификатор документа, из которого взят ответ.
3. Приведи дословную цитату-обоснование.
4. Если документы противоречат друг другу — укажи это явно
   и перечисли обе версии с их источниками.
5. Отвечай кратко, без пересказа документов.

Верни JSON:
{"answer": "...", "doc_ids": ["..."], "quote": "...", "contradiction_found": true|false}

ДОКУМЕНТЫ:
{context}

ВОПРОС: {question}
```

Порядок важен: `{context}` идёт **перед** вопросом, чтобы неизменный префикс попадал в кэш провайдера.

### 11.2 Судья

```
Ты оцениваешь правильность ответа на вопрос по документам.

ВОПРОС: {question}
ЭТАЛОННЫЙ ОТВЕТ: {gold_answer}
ОТВЕТ СИСТЕМЫ: {prediction}

Оценка:
- correct — передаёт тот же факт, что и эталон (формулировка может отличаться)
- partial — часть факта верна, часть упущена или искажена
- incorrect — противоречит эталону или содержит выдуманный факт
- abstain — система заявила, что ответа в документах нет

Верни JSON: {"verdict": "...", "rationale": "одно предложение"}

Оценивай только фактическое совпадение. Стиль и длина значения не имеют.
```

Судья не должен видеть, какой метод породил ответ.

## 12. Ожидаемые результаты и как подать

Гипотезы формулируются **до** прогонов и записываются в `REPORT.md`. Так работа читается как исследование, а не как подгонка под полученные числа.

| Срез | Гипотеза |
|---|---|
| T1, 8K | LC ≈ RAG по accuracy, RAG дешевле в десятки раз → RAG по $/correct |
| T1, 100K | RAG держит качество, LC может просесть → разрыв растёт в пользу RAG |
| T2 | LC лучше; RAG чинится ростом k или декомпозицией запроса |
| T3 | LC заметно лучше; RAG плохо находит противоречия, потому что нужны оба фрагмента сразу |
| Позиция, 8K | эффекта нет |
| Позиция, 100K | провал в середине (воспроизведение Lost in the Middle) |
| Стоимость | LC на 100K дороже RAG на порядок; prompt caching сокращает разрыв для повторных запросов к одному корпусу |

**Любой исход — результат.** Если LC окажется лучше везде, вывод «при текущих ценах на мини-модели RAG не окупается до таких-то объёмов» ничуть не слабее.

### Главная таблица работы

Один экран: строки — методы, колонки — размеры корпуса, в ячейке accuracy и $/correct, разбивка по T1/T2/T3 отдельным блоком. Эта таблица отвечает на исследовательский вопрос целиком.

### Бонус, если останется время (день 7+)

**Роутер по типу вопроса.** Лёгкий классификатор определяет тип вопроса и направляет простые факты в RAG, а сравнения и противоречия — в LC. Замерить accuracy и $/correct роутера против чистых стратегий.

Это превращает benchmark в применимое решение и прямо закрывает формулировку «выводы о практическом применении в KOZ AI». Делать только при готовой основной части.

## 14. Риски

| Риск | Что делать |
|---|---|
| Бюджет кончается на середине | Порядок от дешёвого к дорогому, `cost_guard`, кэш ответов, отладка локально. Даже при полном исчерпании есть результат на 8K/30K. |
| Модель отвечает из общих знаний, а не из контекста | `check_leakage.py` в день 2, брак переписать. Проверка обязательна. |
| Локальная модель не держит 100K | Needle-тест до начала экспериментов. Fallback: 100K только на API, локально 8K/30K, и это указать в отчёте. |
| Сравнение нечестное (разные промпты) | Один `answer.py`, различие только в сборке `{context}`. Прописать в README явно. |
| Внедрённые факты выглядят инородно | Генерировать формулировки в стиле окружающего текста, вычитывать глазами. Если факт заметен «по швам», модель находит его слишком легко. |
| Судья завышает accuracy | Калибровка на 40 ручных примерах, согласованность в отчёт. |
| Одного прогона недостаточно | 3 повтора, среднее ± разброс. Один прогон на защите разберут. |
| Не успеваю | Резать в порядке: HYB → P2 → локальный backend → 100K позиционный → число вопросов 60→40. **Не резать:** точные метрики и 3 повтора. |
